The KINT10d Study Book

A practical education in software engineering AI and quantitative research

KINT10d learning companion • Edition 1 • Research reviewed 15 October 2026

This book teaches the knowledge needed to build three related systems: a dependable trading application, an AI-assisted research agent, and an evidence-driven search for trading strategies. It starts with computer and programming foundations and progresses through market mechanics, data engineering, statistics, machine learning, language models, research automation and production operations.

The goal is independent judgment: being able to explain a system, inspect its evidence, diagnose a failure and decide whether a result deserves further testing. Completing courses alone does not create professional competence or a profitable strategy. The exercises and assessment gates are the essential part of the path. A 10% monthly return remains a research aspiration, not a learning outcome or a promise.

This is an original study guide and project workbook, supported by linked courses, official documentation and research papers. It is not a replacement for the full textbooks. The chapter explanations, examples, exercises and recommended sequence are instructional synthesis; resource descriptions are brief guides to the linked material. All trading examples are hypothetical unless explicitly described as a user-reported case.

How to use this book

Read Chapter 1, then follow the phase plan in Chapter 36. For each chapter, learn the explanation, study the first resource, build the exercise and pass the checkpoint. Use deeper resources when a concept remains unclear or when your project needs them. Do not complete every listed course before writing your first program.

Priority labels: Core means needed for a reliable first system. Next means needed to make the first system robust or research-capable. Advanced means a specialization that can wait. Estimated hours are planning estimates for the exercises and selected reading, not provider-advertised course durations. Full courses take additional time.

Resource labels: Each R-number links to the resource itself. The resource library at the end records format, level, access conditions and verification status. “Opened” means the public page was retrieved during research; it does not mean every video, download or enrolled lesson was consumed. Video links were checked through creator/course pages where possible. Access, fees, quotas, regulations and API examples can change.

First seven days: spend one session mapping the architecture, three sessions on Python functions and files, one on terminal and Git basics, one on market vocabulary, and one building a tiny CSV validator. Use synthetic data. Your first success is a correctly rejected bad row, not a profitable backtest.

1 The systems you are learning to build

Priority: Core. Prerequisites: None. Practice budget: 3–5 hours.

A trading application receives information, makes or receives a decision, checks constraints, manages execution state and reconciles the result. A research system asks whether a decision rule is worth considering. An AI assistant can explain, search, extract and propose; it does not make unreliable input reliable merely by writing a confident summary.

Keep four kinds of evidence separate. A unit test can show that your fee calculation follows its specification. A data audit can show that timestamps and values satisfy a contract. A historical experiment can estimate a strategy's performance under stated assumptions. A prospective observation can show how the system behaves on data it has not already used. None automatically establishes the next.

2 Computer literacy terminal files and environments

Priority: Core. Prerequisites: Chapter 1. Practice budget: 10–15 hours.

A terminal is a text interface to programs. The shell interprets what you type; the operating system manages files, processes, memory and permissions. A running process is not the same thing as a saved script. A file path points to a location; a working directory affects how relative paths are interpreted. These distinctions explain many failures that initially look like Python problems.

Learn absolute and relative paths, quoting, standard input/output/error, exit codes, pipes, environment variables and process IDs. Understand the difference between opening a new terminal, starting a Python interpreter and running a script. Learn to read an error from its first meaningful cause rather than copying the final line into another command.

A virtual environment isolates a project's Python packages. A dependency lock records tested versions. A backup is a recoverable copy; cloud synchronization alone is not a restore plan. A synchronized folder may contain placeholders or changing files. Keep active databases and credentials in a deliberate local location, with a tested backup process and no secrets committed to Git.

The earlier interactive zsh comment error illustrates that a copied script and an interactive shell can interpret input differently. Learn to run a saved script with its declared interpreter, and inspect it before execution. Avoid pasting commands whose purpose you cannot explain.

Exercise: Create a learning folder, write a text file, run a script, redirect its output, deliberately fail it and inspect the exit code. Make a backup and restore it to a different folder. Demonstrate that restoring the copy works without altering the original.

Checkpoint: Find which Python interpreter a project uses, distinguish missing files from permission errors, and explain why deleting a lock file without checking its owner can be unsafe.

Learn in order: R03 shell and environment lessons; R11 virtual environments as a reference. Defer shell customization and advanced automation until ordinary file operations are comfortable.

3 Python from small calculations to maintainable programs

Priority: Core. Prerequisites: Chapter 2. Practice budget: 35–55 hours plus course practice.

Python lets you express a procedure as data and functions. Learn numbers, strings, booleans, lists, dictionaries, conditions, loops and functions before frameworks. A function should have an understandable input, output and error behavior. For example, a candle validator accepts a record and returns explicit violations; it should not silently repair prices while also downloading more data.

Next study file handling, JSON and CSV, exceptions, modules, type hints, dataclasses, iterators and context managers. Learn when a value can be absent, and distinguish 0, an empty string and None. Time handling deserves special attention: use timezone-aware timestamps, retain the original provider timestamp, and avoid comparisons between incompatible types.

Floating-point arithmetic approximates many decimal fractions. That is often acceptable for numerical research with defined tolerances; money, tick rounding and ledger accounting need a deliberate representation such as integer paise or decimal arithmetic. Never let a rounding accident choose a position size.

Read code before asking AI to expand it. Predict a function's output on a small example, run it, then explain any disagreement. Use a debugger and small reproducible inputs. A helpful AI coding request names the input format, expected output and edge cases; “make it work” leaves too much unspecified.

Exercise: Build a command-line program that reads synthetic OHLCV rows, checks required fields and price ordering, and writes a summary. Invalid rows must be retained in a separate error report with reasons. No broker access is required.

Checkpoint: Rebuild the central validation function without copying, explain every line, and handle an empty file, malformed number, duplicated timestamp and missing timezone.

Start here: R01 and its exercise sets. Video-first alternative: R67 with the same exercises. Then use R11 as a reference rather than a first course for a complete beginner.

4 Computer science data structures and performance

Priority: Core fundamentals; advanced algorithms later. Prerequisites: Chapter 3. Practice budget: 15–25 hours.

A data structure organizes information for particular operations. A list is convenient for ordered observations; a dictionary supports lookup by key; a set helps detect duplicates; a queue holds work; a heap efficiently selects the next event by priority. Choosing a structure is a practical design decision, not interview trivia.

Algorithmic complexity describes how work grows with input size. Comparing every tick with every other tick can become expensive quickly. Sorting once and processing observations in time order can be far simpler. Big-O notation ignores constants and hardware details, so measure actual performance after correctness is established.

Learn memory versus disk, CPU-bound versus network-bound work, threads versus processes, and the distinction between asynchronous waiting and parallel computation. A network request spending time waiting may benefit from asynchronous handling; a CPU-heavy calculation needs a different analysis. Concurrency also introduces races: two workers can both believe the last request allowance belongs to them.

For the research agent, performance matters because slow validation can delay decisions and excessive parallelism can exhaust memory or quotas. However, a faster incorrect backtest remains incorrect. Keep a tiny reference implementation even if a larger implementation is optimized.

Exercise: Detect duplicate instrument-timestamp pairs using a slow nested-loop approach and a set. Compare outputs first, then time increasing input sizes. Build a small event queue and prove that events with equal timestamps have a deterministic tie-breaker.

Checkpoint: Explain which operations are constant, logarithmic or linear time in your implementation, and why an unlimited number of concurrent requests is not a scaling strategy.

Start here: R76 selected algorithms/memory lessons. Go deeper: R52 lectures and problems on data structures and sorting. You do not need to finish the entire algorithms curriculum before building the first collector.

5 Git collaboration and reproducible changes

Priority: Core. Prerequisites: Chapters 2–3. Practice budget: 8–12 hours.

Git records source-code history. A commit is a named snapshot; a branch is a movable reference; a diff shows changes; a remote provides another repository location. Git is valuable even for one developer because it makes mistakes inspectable and experiments reversible.

Learn status, diff, add, commit, branch, merge and restore. Understand ignored files, tracked files and untracked files. Ignoring a secret after committing it does not remove the old secret from history. A credential exposure needs rotation and an appropriate cleanup process, not just a new ignore rule.

Use small changes with a clear purpose. A pull request should explain the problem, behavior after the change, validation and remaining limitations. It should not merely list filenames. Pin an experiment to a code commit, but also record data and configuration versions: the same code can produce different results with different data.

When AI proposes a patch, inspect the diff and ask what assumptions changed. A plausible fix can silently loosen a quality threshold or reset a budget. Treat policy and protocol changes as first-class changes, not incidental implementation details.

Exercise: Create a learning repository containing the validator. Introduce a bug on a branch, write a test that exposes it, fix it and review the diff. Restore an older version into a separate directory and reproduce its behavior. Keep all sample data synthetic and all credentials absent.

Checkpoint: Recover a previous version without deleting current work, explain why unpushed files may not exist on GitHub, and distinguish code backup from database backup.

Start here: R04 Git Basics and Branching. R03 supplies a video-based alternative. Keep one written recovery drill in your project notes.

6 Software design testing and debugging

Priority: Core. Prerequisites: Chapters 3–5. Practice budget: 20–30 hours.

Software engineering turns a collection of scripts into behavior people can depend on. Start with requirements expressed as observable outcomes: “a stale quote must be rejected with its age” is testable; “make the system reliable” is not.

Separate pure calculations from side effects. A fee calculation should not contact a broker. A data parser should not decide whether a strategy is profitable. A repository or adapter boundary makes external dependencies replaceable for tests. Prefer composition of small components over elaborate inheritance hierarchies.

Use several testing layers. Unit tests check focused logic. Contract tests check external response assumptions. Integration tests check components together. End-to-end tests check a complete user workflow. Property tests check invariants over many inputs: for valid candles, high must not be below low; replaying the same completed job should not duplicate output. Mutation-style thinking asks whether a test would fail if the implementation were meaningfully wrong.

Debug scientifically: reproduce, narrow the failing component, state a hypothesis, change one relevant thing and observe. Distinguish HTTP success from business success and both from valid market data. Avoid catch-all error handling that converts every failure into “no signal.”

Exercise: Give a fake provider five behaviors: valid response, malformed JSON, expired authentication, timeout and duplicate page. Demonstrate distinct outcomes and bounded retries. Add a test that proves a rejected credential update preserves the previous file.

Checkpoint: Explain what your tests do not prove. In particular, software verification does not prove market-data accuracy or strategy profitability.

Start here: R12. Next: R13 for property-based tests and R54 for automated checks. Apply those tools to meaningful failures; do not chase a coverage percentage by testing trivial code.

7 Mathematics for models and risk

Priority: Core algebra; calculus and optimization next. Prerequisites: Basic arithmetic. Practice budget: 25–45 hours.

Begin with ratios, percentages, fractions, exponents and logarithms. A price moving from 100 to 110 rises 10%; falling from 110 back to 100 loses about 9.09%. Returns compound multiplicatively, which is why averaging percentages can mislead.

Vectors are ordered lists of numbers; matrices organize many vectors. A feature matrix might have one row per observation and one column per measured attribute. A dot product combines features with weights. Matrix dimensions should be explicit: mixing observations and features produces errors that can look numerically plausible.

Derivatives measure local sensitivity. If a small price change produces a large change in option value, sensitivity matters even when the original position looks cheap. Gradients collect sensitivities across parameters. Optimization changes parameters to improve an objective, subject to constraints. Learning the objective and its limitations is more important than memorizing an optimizer's name.

Numerical methods have tolerances and stability limits. An almost singular covariance matrix can create extreme portfolio weights. Rescaling features may improve numerical behavior, but fitting the scaler on future data creates leakage. Mathematics and data timing therefore cannot be separated.

Worked example: If monthly capital grows by 10% for twelve consecutive months, the multiplier is 1.1^12 ≈ 3.138, a gain of about 214%. That arithmetic illustrates how demanding the aspiration is; it is not a forecast. A 20% drawdown requires 25% growth to recover because 0.8 × 1.25 = 1.

Exercise: Calculate simple and log returns on five synthetic prices. Multiply small matrices by hand and in NumPy. Plot a quadratic loss and implement a few gradient-descent steps.

Checkpoint: Explain dimensions, compounding and sensitivity without relying on an AI-generated derivation.

Start here: R09 for intuition and R23 for systematic study. Use R38 to connect the mathematics to arrays.

8 Probability and decision making under uncertainty

Priority: Core. Prerequisites: Chapter 7 algebra. Practice budget: 25–40 hours.

Probability describes uncertainty under a model. A random variable represents a quantity whose outcome is not known in advance. Expectation is a weighted average over possible outcomes, not a promise for the next observation. Variance measures dispersion; dependence describes how outcomes move together.

Conditional probability is central to trading research. The probability of an upward move among all stocks is different from the probability after a particular filter. Bayes' rule combines prior information with evidence, but the quality of the result depends on the assumptions and evidence quality. A model's verbal confidence is not a measured probability.

Learn Bernoulli and binomial models, normal distributions as approximations, heavy tails, covariance and correlation. Markets can have clustered volatility and dependent outcomes. Ten trades on the same market move are not necessarily ten independent pieces of evidence. A simple independent coin-flip model is useful for learning, but may understate real risk.

Worked example: Suppose a hypothetical rule wins ₹200 with probability 0.40 and loses ₹100 otherwise. Gross expectation is 0.40×200 − 0.60×100 = ₹20. If expected round-trip cost is ₹25, net expectation is −₹5. A 2:1 reward-to-risk ratio alone does not establish an edge. Before costs, the break-even win probability for those fixed payoffs is one-third; costs raise it.

Exercise: Simulate repeated trades with a fixed seed, then repeat with clustered losses. Compare cumulative returns and drawdowns despite matching average win rates. Explain which assumptions were deliberately unrealistic.

Checkpoint: Distinguish conditional probability, average payoff and maximum possible loss. Explain why a profitable average does not make every trade desirable.

Start here: R21 interactive probability. Go deeper: R22 probability lectures and exercises. Use R10 expected-value and conditional-probability videos when intuition is missing.

9 Statistics inference and the habit of skepticism

Priority: Core. Prerequisites: Chapter 8. Practice budget: 25–40 hours.

Statistics uses samples to reason about a broader process. An estimate needs uncertainty: a mean profit of ₹10 based on a few dependent observations may be much less informative than it sounds. Distinguish standard deviation, describing variation in observations, from standard error, describing uncertainty in an estimator under assumptions.

A p-value measures how surprising a result or something more extreme would be under a specified null model. It is not the probability that the strategy is false, and a threshold does not measure economic usefulness. Confidence intervals also depend on a sampling procedure and assumptions. A narrow but biased estimate can be confidently wrong.

Learn effect sizes, sampling bias, statistical power, confidence intervals, bootstrap resampling, multiple testing and false discovery rates. Repeatedly changing a strategy after observing results creates selection bias. Keep a record of failed variants, not only the attractive chart you finally retain.

Financial observations often violate independent-identically-distributed assumptions. Resampling whole days or dependent blocks may be more defensible than resampling individual trades, depending on the design. Block length, regime changes and the limited amount of data remain modeling choices, not automatic fixes.

Exercise: Generate noise, test many arbitrary filters and find the best-looking one. Evaluate that winner on fresh noise. Record all trials. Then compare confidence intervals that treat observations as independent with intervals grouped by synthetic day.

Checkpoint: Explain how you could obtain a statistically impressive backtest without any genuine predictive information. State what data would make you reject your favorite hypothesis.

Start here: R69 and R71 videos, then R06 inference and resampling material. Advanced: R47 and R48 after Chapter 20; these methods address particular biases, not every source of research error.

10 SQL and the design of a research ledger

Priority: Core. Prerequisites: Chapter 3. Practice budget: 15–25 hours.

A relational database stores structured records with constraints. SQL asks questions about those records. Learn tables, rows, keys, filtering, aggregation, joins and window functions. A primary key identifies a record; foreign keys connect related records; a unique constraint can prevent duplicate observations or duplicate job registration.

Design separate entities for instruments, raw requests, observations, dataset versions, experiments and events. A symbol is not always a durable identifier. Derivatives need exchange, underlying, instrument type, expiry, strike and option right as appropriate, with the actual provider identifier preserved.

Transactions group changes into a unit that either commits or rolls back. This matters when two workers reserve a quota or claim a job. A read followed by a write outside a transaction can race. Indexes accelerate selected queries but cost storage and write work; measure the queries you actually need.

SQLite is a reasonable starting point for a small local ledger. A server database such as PostgreSQL becomes useful when concurrency, remote access or operational requirements justify it. Moving databases does not repair a poor schema. Analytical files and operational ledgers have different purposes.

Exercise: Create an experiment table with a unique experiment ID, protocol hash, data hash, status and creation time. Create an event table linked to it. Query the most recent completed run and all blocked runs by reason. Demonstrate a failed transaction leaving no partial reservation.

Checkpoint: Distinguish “the process is alive” from “a completed experiment exists” using queries alone. Explain how a duplicate job is prevented rather than merely hidden in the dashboard.

Start here: R02. Reference: R39 when learning database transactions and scaling. Do not put credentials or raw account responses in the educational database.

11 Data analysis with NumPy pandas and charts

Priority: Core. Prerequisites: Chapters 3, 7 and 10. Practice budget: 20–30 hours.

NumPy handles numerical arrays; pandas adds labelled tables and time-aware operations. Learn indexing, filtering, grouping, joins, missing values, sorting, resampling and rolling calculations. Before plotting a result, know what each row represents and what the units mean.

A join can silently multiply records if keys are not unique. A resample can silently assign a boundary observation to the wrong candle. A rolling mean can include the current observation when the decision was supposed to occur before it. These are research errors, not just programming details. Write small examples where you know the answer by hand.

Keep a notebook for exploration and communication, but move important transformations into tested functions. Restart the notebook and run it from top to bottom: hidden state can make a result impossible to reproduce. Record timezone, adjustment policy and sort order explicitly.

Charts should answer questions. A price chart shows path; a return distribution shows dispersion; a cumulative equity curve shows compounding; a drawdown chart shows decline from a prior peak. Use honest axes, units, sample counts and dates. Show missing periods rather than drawing an uninterrupted line across an outage.

Exercise: Construct ten one-minute candles with known values. Aggregate them into two five-minute candles and verify first open, maximum high, minimum low, last close and summed volume. Deliberately remove a minute and decide whether the aggregate is invalid, partial or acceptable under a documented policy. Never invent a missing traded price to make the chart look continuous.

Checkpoint: Explain why summing volume can be correct while summing open interest is usually not the desired end-of-period measure. Explain whether a provider reports incremental or cumulative volume before calculating either.

Start here: R38 followed by selected chapters of R05. Use the project's actual schema only after the synthetic exercise works.

12 Market data engineering and point in time correctness

Priority: Core. Prerequisites: Chapters 10–11 and basic market vocabulary. Practice budget: 25–40 hours.

Data engineering makes observations trustworthy enough for a defined use. Preserve raw responses, normalize into a documented schema, then qualify the result. Record provider, instrument identity, request parameters, retrieval time, source event time, timezone, session phase and transformation version. Raw data should remain recoverable even when a transformation is corrected.

The central question is: what could the system have known at this decision time? A revised corporate announcement, a later-retrieved pre-open snapshot or today's index constituents cannot automatically be used in yesterday's experiment. Store availability time as well as the time the event describes. Point-in-time joins select only information available at the simulated decision.

Understand corporate actions, symbol changes, delistings, survivorship bias, adjusted versus unadjusted prices, auction periods and exchange calendars. Never infer universal candle counts from one recent day. Session rules can vary by date and eligibility. Provider agreement is useful but not proof of independence if both vendors share an upstream feed.

Design idempotent chunks: fetching the same instrument/date/interval twice should not duplicate accepted observations. Quarantine discrepancies with a reason and a resolution record. An empty response can mean no trading, no entitlement, an invalid instrument or a provider failure; it needs classification.

Exercise: Build raw, normalized and qualified layers for synthetic data. Inject a split, a renamed instrument, a late observation, a missing bar and an auction print. Produce a report that distinguishes each condition. Save a content hash and the exact transformation version.

Checkpoint: Reconstruct a dataset version from raw inputs and explain why daily OHLC may differ from an aggregation of a restricted intraday session.

Resources: R40 for columnar storage, R44 for current session reference, R43 for contracts and R05 for transformations. Reading access does not imply permission to redistribute market data.

13 APIs networking and secure broker integration

Priority: Core. Prerequisites: Chapters 3, 6 and 12. Practice budget: 20–30 hours.

An API is a contract between programs. HTTP requests have a method, address, headers and possibly a body; responses have a status and content. Learn DNS, TLS, JSON, timeouts, authentication, authorization, pagination and rate limits. HTTP 200 says the HTTP exchange succeeded; inspect the provider-level status and returned data too.

API keys identify applications; secrets and tokens serve different roles. Follow the provider's precise authentication scheme. For signed requests, timestamp and body bytes may matter. Never assume successful login proves every endpoint works. In the KINT10d diagnosis, duplicated API and secret values were compatible with a login path but prevented the signed quote path from authenticating correctly; a controlled request after correction established access.

Retry transient failures with a bounded policy and backoff. Stop on authentication failures until resolved. A timed-out read can usually be retried more safely than a side-effecting operation, but quotas still apply. In an execution design, uncertain order submission requires reconciliation rather than blind resubmission.

Separate provider quotas from local budgets. Breeze's published FAQ stated 100 calls per minute and 5,000 daily when reviewed; KINT10d's lower local limits are application controls. Keep one coordinated budget across participating callers and leave headroom for other account usage. Streaming changes the access pattern but is not unlimited or automatically reliable. R46 is the source for the published limit.

Exercise: Use a fake HTTP service to simulate 200 with malformed data, 401, 429 and a timeout. Implement a persistent request ledger, redacted logs and a freshness check. Do not use live credentials in tests.

Checkpoint: Explain the difference between authentication, authorization, endpoint allowlisting, data freshness and request budgeting.

Start here: R53, then R45 and R20. Verify current provider documentation before implementing a real connector.

14 Indian markets accounting and economic context

Priority: Core. Prerequisites: Arithmetic; coding can be learned alongside this chapter. Practice budget: 20–35 hours.

Learn what a share represents, how a company raises capital, how exchanges and brokers differ, and why clearing and settlement exist. Know the roles of demat holdings, trading accounts, cash balances, obligations and margin. Distinguish an index from a tradable instrument linked to it.

Read basic financial statements: the income statement measures performance over a period; the balance sheet describes assets and claims at a point in time; the cash-flow statement follows cash movement. Revenue growth, earnings and cash generation are different. A news headline should be checked against the underlying filing, its publication time and what was already expected.

Economic context includes interest rates, inflation, currency movements, sector exposure and scheduled announcements. These can help formulate hypotheses, but an explanatory story after a move does not establish a predictive mechanism. Distinguish prediction from causal explanation and relative strength from intrinsic valuation.

For India, learn primary versus secondary markets, equity versus derivatives, settlement obligations, corporate actions, market-wide restrictions and broker risk controls. Exact rules, tax rates, contract terms and fees belong in dated reference tables, not in memory or hard-coded assumptions. Use NISM as a structured syllabus and NSE/SEBI for current authoritative details.

Exercise: Write an instrument fact sheet for a hypothetical equity and a hypothetical index future. Identify issuer/underlying, trading venue, unit of exposure, settlement mechanism, relevant costs and sources that would need refreshing. Write a one-page company summary from an annual report without turning it into a buy recommendation.

Checkpoint: Explain why price strength, company quality and a tradable short-horizon edge are distinct questions.

Start here: R08 introductory and fundamental-analysis modules; R41 as a completeness checklist. Broader context: R50. Its older US lectures teach concepts, not current Indian procedures.

15 Market microstructure and execution realism

Priority: Core for intraday research. Prerequisites: Chapter 14. Practice budget: 20–30 hours.

Market microstructure studies how orders become trades. The best bid is a displayed buying price and the best ask a displayed selling price. Their difference is the spread. Last traded price describes a completed trade, not necessarily the price available to you now. Displayed depth can change before your order arrives.

Understand market and limit orders, stop triggers, partial fills, queue priority, cancellations, auctions, price bands and trading halts. Price-time priority means a limit price alone does not establish where your order sits in the queue. A candle touching a limit is not proof of a fill. A stop level is not a guarantee of the eventual exit price.

Latency includes data transport, processing, decision time and execution acknowledgement. A five-minute scheduled check can miss a condition that exists for seconds. Its claims should match its observation frequency. Record event time, receive time and decision time separately.

Execution simulations need an explicit model for spread, slippage, liquidity and adverse selection. Increasing order size may worsen results; historical returns calculated at the mid-price do not include that effect. Bid/ask snapshots are better than last price for some questions, but snapshots still do not reveal the entire execution path.

Exercise: Replay a toy order book containing several price levels. Simulate a market buy larger than the best ask quantity and calculate its volume-weighted fill. Then simulate a passive limit order behind existing quantity and explain why the next trade does not necessarily fill it.

Checkpoint: Give three reasons an attractive candle-based result might be untradeable. Distinguish pre-open indications from actual fills.

Start here: R65 and R66. Application: R37 for explicit reality models. Confirm Indian-market assumptions independently rather than importing a foreign-market default.

16 Futures options and derivatives risk

Priority: Next; required before derivatives experiments. Prerequisites: Chapters 7–8 and 14–15. Practice budget: 30–50 hours.

A future creates exposure to an underlying through a contract with defined terms. An option grants a specified right in exchange for a premium. Learn contract multipliers, expiry, strike, call/put, intrinsic and time value, margin, marking to market, exercise and settlement. Buying a low-premium option is not equivalent to taking small economic risk in every relevant sense: liquidity and total premium loss still matter.

Delta measures local sensitivity to the underlying; gamma describes how delta changes; theta reflects time sensitivity; vega reflects volatility sensitivity. These are model-based local descriptions, not fixed guarantees. Option value can fall despite a favorable underlying move if other influences dominate. Implied volatility is inferred from a pricing model; it is not the same quantity as realized future volatility.

Study payoff diagrams first, then binomial pricing, no-arbitrage reasoning and basic Black–Scholes assumptions. Learn volatility smiles, term structure, hedging error and model risk later. Pricing a derivative and forecasting a profitable trade are different tasks.

A derivatives dataset needs full contract identity and historical specifications. Expired contracts, changes in lot size, sparse trading and settlement prices require specific treatment. Open interest, traded volume and quote liquidity measure different things. Avoid manufacturing continuous option histories by joining contracts without a declared rule.

Exercise: Build payoff tables for a long call, long put and future using fictional multipliers. Separate payoff at expiry from profit after premium and costs. Show how the same premium move creates different rupee exposure under different lot sizes. Reject a simulated position when the smallest legal lot exceeds the approved budget.

Checkpoint: Explain why a ₹20,000 account balance alone says little about the suitability of a derivatives position.

Start here: R08 derivatives modules, then R49. Reference: R42, R43 and R51. Use current exchange/broker rules for settlement and margin; this book does not freeze those values.

17 Costs position sizing portfolio risk and accounting

Priority: Core. Prerequisites: Chapters 8 and 14–16 as applicable. Practice budget: 20–30 hours.

A strategy earns what remains after costs and implementation effects. Build a dated fee model for the actual segment and broker plan, covering applicable brokerage, exchange charges, statutory levies and taxes. Model spread and slippage separately unless intentionally included in a single execution-price assumption; avoid counting them twice. Income-tax treatment and transaction-level charges are different questions.

For a long cash position, planned price risk is quantity times the entry-to-stop distance. A capital constraint, lot constraint, liquidity constraint and all-in loss allowance can each impose a lower quantity. Margin is collateral required to hold exposure; it is not the maximum loss. A gap or failed exit can exceed planned stop risk.

Hypothetical example: Capital ₹10,000 with 25% reserved leaves ₹7,500. Entry ₹100, stop ₹98 and all-in planned loss budget ₹50. Assume for teaching only a conservative ₹10 total loss-side friction reserve. Risk permits floor((50−10)/2)=20 shares; cash permits 75. Choose at most 20 before other constraints. At a ₹104 target and ₹10 winning-side friction, planned net reward is ₹70 and loss is ₹50: only 1.4:1. A ₹105.50 target would give ₹100 net reward under those assumptions, but a formula cannot make that target plausible. Actual costs can depend on quantity, requiring iteration.

Portfolio risk also includes correlated positions, sector concentration, volatility changes, drawdown, cash usage and tail events. Learn exposure aggregation before optimization. Keep research capital assumptions separate from the manual-session settings.

Exercise: Build a synthetic ledger showing cash, fees, realized P&L, unrealized P&L and equity after every event. Make the ledger reconcile exactly. Test fee changes, gaps and rejected position sizes.

Checkpoint: Explain why a price-risk budget, an all-in planned loss budget and worst-case loss are not interchangeable.

18 How to formulate a trading hypothesis

Priority: Core. Prerequisites: Chapters 9, 12 and 14–17. Practice budget: 15–25 hours.

An edge hypothesis is a falsifiable statement about conditional net outcomes. “Strong stocks go up” is too vague. A useful proposal specifies the eligible universe, information timing, measurable signal, entry and exit rules, costs, baseline and evidence that would count against it.

Study broad strategy families: trend or momentum, mean reversion, cross-sectional ranking, event-driven effects, carry and volatility risk premia, and statistical relative value. Learn the economic intuition and failure modes of each before searching parameters. A compensation for bearing crash risk can look like a stable edge until the crash arrives. A pattern visible only after selecting today's winners is selection bias.

An illustrative stock-selection case is a good hypothesis source but weak validation. The reported process began with two names, noted pre-open sector alignment and post-open strength, then narrowed attention. It did not establish a complete market ranking, time-of-day relative volume or a qualified entry before the later rise. Preserve that distinction.

A prospective study could compare a fixed opening-range rule with and without pre-open sector filters across an eligible point-in-time universe. The range length, data availability policy and target construction must be frozen before evaluating results. Include non-triggers and failures; do not study only the names that attracted attention.

Exercise: Write three one-page hypothesis cards. Each must include mechanism, null hypothesis, data requirements, causal features, baseline, cost assumptions, variant budget and rejection criteria. Select the cheapest one to test credibly, not the most exciting story.

Checkpoint: Describe an outcome that would cause you to retire the hypothesis. Explain why the motivating example belongs to development context rather than untouched confirmation data.

19 Backtesting as an event simulation

Priority: Core. Prerequisites: Chapters 6, 12, 15 and 17–18. Practice budget: 30–45 hours.

A backtest is a simulation of decisions under historical information constraints. A vectorized calculation is useful for exploration, but a realistic trading system also needs an event sequence: observation arrives, feature becomes available, signal is evaluated, risk is checked, an order is simulated, a fill occurs and the ledger changes.

Specify the clock. A strategy based on a completed candle cannot generally fill at that same candle's earlier open. A five-minute candle that contains both a stop and a target does not reveal which was reached first. Choose a conservative ambiguity policy or obtain finer data; do not choose the profitable order after seeing the result.

Separate signal generation from portfolio accounting and execution assumptions. Keep a simple reference engine and reconcile a small set of trades by hand. Include fees, spread, slippage, cash constraints, lot sizes, missing observations, trading calendars and corporate actions. Record every rejection and every simulated fill assumption.

Benchmark the strategy against relevant alternatives: doing nothing, a simple exposure-matched rule or another predefined baseline. A profitable period in a rising market may not demonstrate useful timing. Compare risk and exposure, not only total return.

Exercise: Create a synthetic day with ten bars and one possible signal. Hand-calculate the expected ledger. Then add a gap through the stop, simultaneous stop/target touches, a missing bar and insufficient capital. The engine must report its assumptions and produce the expected state for each case.

Checkpoint: Reproduce the same output from a clean environment with the same data, protocol and code hashes. Explain any allowed numerical tolerance.

Start here: R37 for modeling components. Pair with R12 for engine tests. No off-the-shelf backtest engine should be treated as automatically accurate for a particular broker or instrument.

20 Validation multiple testing and confirmation

Priority: Core. Prerequisites: Chapters 9 and 18–19. Practice budget: 25–40 hours.

Training data estimates parameters. Validation data supports development choices. Confirmation data is reserved for a final, predefined assessment. If you repeatedly inspect confirmation outcomes and revise the strategy, that set becomes development data. A folder named “test” cannot prevent this contamination.

Use chronological evaluation for time-dependent decisions. Overlapping label horizons can leak information across split boundaries. Purging removes training examples whose outcome windows overlap evaluation windows; an embargo or gap can reduce nearby dependence under a specified design. A generic time split does not automatically solve all leakage, and a gap should reflect the actual information horizon.

Compare multiple development periods, instruments and conditions. Report uncertainty and sample concentration: a strategy supported mainly by one unusual day is different from one with distributed evidence. Test cost sensitivity and parameter stability without treating every additional test as free evidence. Keep a trial ledger including abandoned variants and manual revisions.

Sharpe ratio summarizes mean excess return relative to variability under a stated sampling convention. Autocorrelation, nonnormality, short samples and selection can distort its interpretation. Deflated Sharpe and probability-of-backtest-overfitting methods address particular aspects of this problem and require careful assumptions; they do not certify an edge. R47 and R48 provide the advanced research readings.

Exercise: Register a small fixed comparison before running it. Produce results by time block, confidence intervals under a justified dependence model, cost-stress results and a complete variant list. Write the conclusion before deciding what to try next.

Checkpoint: A reviewer must be able to distinguish exploratory findings, validation findings and untouched confirmation. Zero convincing evidence is a legitimate result.

Start here: R25 and R24 for implementation pitfalls; R70 teaches generic cross-validation intuition. Its ordinary random-fold examples are not a ready-made validation recipe for financial time series.

21 Time series forecasting and changing markets

Priority: Core concepts; specialized models next. Prerequisites: Chapters 9 and 11. Practice budget: 20–35 hours.

A time series is an ordered sequence whose dependence matters. Learn lags, autocorrelation, trend, seasonality, stationarity and structural change. A high correlation between two trending price series can be misleading; returns, differences and economic reasoning help frame the right question.

Start forecasting with simple baselines: last value, historical mean or an appropriate seasonal reference. Study residuals and forecast errors before sophisticated models. A volatility forecast, a direction forecast and a probability of hitting a barrier are different targets. A model useful for one may be poor for another.

Intraday data often has time-of-day patterns in activity and volatility. Compare a morning observation with a suitable morning baseline, not an arbitrary full-day average. Estimate such baselines only from information available at that time. Nonstationarity means yesterday's relationship may change; it does not justify explaining away every failed result as a new regime.

Study ARIMA and volatility models as conceptual tools after understanding evaluation. Use walk-forward evaluation to mimic repeated historical forecasting. Re-estimation frequency, lookback windows and drift thresholds are part of the protocol and can themselves be overfit.

Exercise: Forecast a synthetic seasonal series with naive and fitted models. Introduce a structural break and compare rolling errors. Then design a time-of-day volume baseline without using later observations from the current day.

Checkpoint: Explain why a low price-forecast error does not automatically create profitable trades after costs. State what drift would trigger investigation and what would merely be normal variation.

Start here: R07. Its examples use R; focus on the statistical ideas and reproduce a small example in Python only after understanding the reference. R25 supports chronological evaluation, and R05 supports time-series manipulation.

22 Machine learning from regression to calibrated decisions

Priority: Core for the planned baseline. Prerequisites: Chapters 7–11 and 20. Practice budget: 30–50 hours.

Machine learning estimates patterns from examples. Supervised learning uses inputs and known targets; unsupervised learning seeks structure without the same target format. A model is a function with parameters, a loss function tells training what errors to penalize, and optimization adjusts parameters using training data.

Begin with linear regression and logistic regression. Logistic regression maps a weighted feature combination through a sigmoid to estimate a class probability. L2 regularization penalizes large coefficients. Understand feature scaling, missing values, class imbalance, threshold selection and calibration before adding trees or boosting.

Evaluate the quantity the system needs. Accuracy may reward predicting the dominant class. AUC measures ranking across thresholds, not expected trading profit. Calibration asks whether predicted probabilities align with observed frequencies. A model with impressive classification metrics can still fail after costs or on the subset where execution is possible.

Use a pipeline so transformations are fit on training data and applied consistently later. Preserve seeds and software versions, but recognize that seeds alone do not guarantee reproducibility across all hardware and numerical libraries. Compare a simple baseline before increasing complexity.

KINT10d's previously approved fixed logistic baseline and feature set are protocol choices. The exercises here teach alternatives; they do not authorize changing that research protocol or tuning its regularization against confirmation results.

Exercise: Train a logistic classifier on a synthetic dataset with known structure. Compare against a constant-probability baseline. Plot calibration, inspect mistakes and demonstrate the misleading result obtained by leaking the label into a feature. Remove the leak and report the change.

Checkpoint: Explain parameters versus hyperparameters, discrimination versus calibration, and model quality versus strategy performance.

Start here: R06 Python edition. Video support: R73 and R10 logistic-regression lessons. Implementation safeguards: R24.

23 Financial features labels and alternative data

Priority: Core. Prerequisites: Chapters 12, 20–22. Practice budget: 20–35 hours.

A feature is a measurable input available at decision time. A label describes the outcome being learned. A feature formula should specify its window, timestamp convention, missing-data policy and units. “Momentum” is a topic, not a complete feature definition.

Examples to study include lagged returns, realized volatility, range position, relative volume, spreads, market/sector returns and event indicators. Indicators are transformations of data; collecting many correlated indicators does not necessarily add independent information. Features chosen after looking at their apparent success count as research choices.

Labels need equally careful definitions: return over a fixed future horizon, direction after costs, or which of two barriers is reached first. Overlapping horizons create dependence and complicate validation. A label based on a future maximum may describe an opportunity that a real-time decision could not capture.

Alternative data introduces publication and revision problems. A news item has publication time, retrieval time and possibly an updated version. Sentiment extracted by a current language model may reflect knowledge learned after the historical event. Historical simulation must address this contamination rather than assuming text processing is automatically causal.

Feature importance is not causality. Correlated inputs can redistribute importance; a model may use a convenient proxy that disappears later. Start with a small interpretable set and write an ablation plan before comparing variants.

Exercise: Write a feature contract for five proposed inputs. For each, state the latest source observation allowed and construct a future-data test that would expose leakage. Label synthetic events with explicit start and end times and identify overlapping examples.

Checkpoint: Given any feature value, trace it back to raw observations and prove they were available before the decision.

24 Deep learning reinforcement learning and what can wait

Priority: Advanced except basic intuition. Prerequisites: Chapters 7, 8 and 22. Practice budget: 25–40 hours for foundations; specialization takes longer.

A neural network composes parameterized transformations. Training compares predictions with targets, computes gradients through the network and updates weights. Learn tensors, activations, loss functions, backpropagation, batching and overfitting. Start with a small model you can inspect; training a large language model from scratch is not required for KINT10d.

Deep learning can be useful for text, document extraction and complex representations. It also adds data requirements, compute costs and debugging challenges. A simple model with clean data can be a better research baseline than a sophisticated architecture evaluated poorly.

Reinforcement learning studies decisions that influence future states and rewards. Learn states, actions, policies, rewards, exploration and value estimation. In trading, the simulator defines what the learner experiences. If it grants unrealistic fills or hides costs, the agent can learn to exploit the simulator rather than the market. Offline evaluation and distribution shift are major challenges.

Keep a specialization map: stochastic calculus for advanced derivatives pricing; optimization for constrained portfolios; causal inference for economic identification; reinforcement learning for sequential decision research; high-performance computing for demonstrated bottlenecks. These are valuable paths, not prerequisites for the first reliable collector and baseline experiment.

Exercise: Train a tiny neural network on a nonfinancial toy task. Compare its errors and runtime with a simple model. Separately write a toy sequential environment where the reward mistakenly omits a transaction cost, and show how that changes the apparent best behavior.

25 How language models work

Priority: Core intuition; architecture details next. Prerequisites: Chapter 3; Chapters 7 and 24 for mathematical depth. Practice budget: 12–20 hours.

A language model converts text into tokens, represents them numerically and computes a distribution over possible continuations. Training adjusts its parameters using large amounts of data; inference uses those parameters with the current context. Post-training can improve instruction following and other behaviors, but it does not turn every generated claim into verified knowledge.

An embedding is a numerical representation that can capture useful relationships. Attention combines information from different positions in a sequence. A transformer stacks such operations with other components. Context length limits what can be considered at once; compression and retrieval change what information is available.

Fluency, factual accuracy, reasoning and tool access are separate capabilities. A model without current market data cannot know a fresh quote simply because the question asks for one. A model with a browser still needs to check source timestamps. A tool response can be incomplete, stale or malicious.

Distinguish training, fine-tuning, retrieval and prompting. Prompting changes the input; retrieval supplies external material; fine-tuning changes model behavior through additional training. None is universally the right first intervention. For a paper assistant, improving extraction and retrieval may be more valuable than fine-tuning.

Exercise: Ask a model to answer questions about a small document, including one unanswerable question and one containing a false premise. Score evidence and abstention rather than eloquence. Repeat with and without relevant passages and compare failures.

Checkpoint: Explain why an LLM is useful for translating a paper into a candidate implementation specification but should not be the sole judge of its own correctness.

Start here: R68, then R27. Advanced: R57 and R72 after R28 foundations. These resources explain mechanisms; no particular model family is assumed to remain best over time.

26 Prompting context engineering and AI assisted coding

A good prompt defines an objective, necessary context, input evidence, constraints and an observable output. Include examples when they clarify the task. Separate trusted instructions from retrieved documents. Ask for uncertainty and missing information to be represented explicitly. More words are not inherently better; irrelevant context can obscure the decision.

27 Retrieval augmented generation and research memory

Priority: Next. Prerequisites: Chapters 10, 12 and 25–26. Practice budget: 20–35 hours.

Retrieval-augmented generation supplies relevant external material before generating an answer. The pipeline typically ingests documents, extracts text, splits it into passages, indexes those passages, retrieves candidates and generates a response with citations. The original RAG paper is a useful historical reference; modern systems differ in implementation.

28 Agents tools workflows and bounded autonomy

Priority: Next. Prerequisites: Chapters 6, 13 and 25–27. Practice budget: 20–35 hours.

An agent combines a model with tools, state and a control loop. A workflow follows a predefined sequence or graph; an agent may choose among permitted next steps. More autonomy expands the set of possible failures. Begin with a bounded workflow and add choice only where evaluation shows a benefit.

Tool schemas describe inputs and outputs. The application decides whether a requested operation is permitted, validates arguments and executes it. A model-produced tool call is a proposal, not an authorization. MCP standardizes aspects of connecting tools and resources; it does not establish trust, guarantee correctness or remove the need for access controls.

Design budgets for requests, time, tokens, storage and retries. Persist checkpoints so an interrupted job resumes without silently starting a new experiment or duplicating output. Separate research permissions from execution permissions. An educational research agent can collect approved evidence, summarize it and propose a study while having no order capability.

Multiple agents are an optional coordination pattern. Shared inputs, explicit ownership and independent verification matter more than agent count. Two agents repeating the same mistaken assumption are not independent evidence. A scheduler should wake a bounded job, not create an unbounded loop of agents reviewing one another.

Exercise: Build an offline workflow with three tools: list local documents, extract a passage and write a hypothesis draft. Add a maximum of five tool calls, a timeout and a persisted state. Inject an unsupported tool request and prove that the application rejects it.

Checkpoint: Explain exactly what happens after interruption, budget exhaustion, a tool error and an attempted unauthorized action.

29 AI evaluations security and human oversight

31 Services concurrency and durable workflows

Priority: Next. Prerequisites: Chapters 4, 10 and 13. Practice budget: 20–35 hours.

A service is a program that provides a capability to other programs or users. Learn processes, network ports, request handling, queues, locks and durable state. Keep a service interface narrow: a data reader should not silently alter the research protocol, and a dashboard page load should not launch an experiment.

Failures can occur between any two steps. A worker may claim a job and crash before writing output; it may write output and crash before marking completion. Use job identifiers, leases or locks as appropriate, transactional state changes and idempotent output handling. “Exactly once” is difficult across separate systems; design for duplicate delivery and explicit reconciliation.

Learn backpressure: when work arrives faster than it can be processed, a bounded queue should slow or reject intake rather than grow until memory runs out. Separate retryable failures from permanent rejections. A circuit breaker temporarily stops calls after a defined failure pattern so an outage does not become a retry storm.

Persist resource budgets. Restarting a process should not reset the day's request count or allow an exhausted experiment budget to start over. Use monotonic clocks for elapsed durations and timezone-aware wall clocks for audit timestamps. On a laptop, sleep, network changes and disk pressure are ordinary operational events, not rare exceptions.

Exercise: Build a fake chunk collector with a database-backed queue. Terminate it after claiming work and again after writing a chunk. Restart and verify no duplicate qualified rows, no lost completed work and an intelligible recovery log.

Checkpoint: Explain the difference between a process lock, a database transaction and an idempotency key. Identify the scope each protects.

Final oral test: Explain a randomly chosen run from raw input to final conclusion. Reproduce it, show a failure case and identify the strongest reason the conclusion could be wrong. If you cannot do that without the AI narrating for you, revisit the relevant chapter.

Resources: R12, R24, R30 and R60 support the different assessment layers. Do not merge model evaluations, software tests and trading validation into a single score.

Appendix C Worked reasoning exercises and answers

Attempt each question before reading its answer. Numbers are hypothetical and do not represent current broker charges or market observations.

1 A percentage trap

A portfolio rises 20% and then falls 20%. What is the total return?

Answer: 1.2 × 0.8 − 1 = −4%. The arithmetic average of the two returns is zero, but the compounded return is negative. Use the correct return definition in reports.

2 A reward to risk trap

A rule wins ₹200 or loses ₹100, with a 40% win probability and ₹25 expected cost per trade. Is the expected net result positive?

Answer: No. 0.4×200 − 0.6×100 − 25 = −₹5. Win probability and costs are necessary; the payoff ratio alone is insufficient.

3 A timing trap

A snapshot describes 09:05 but is retrieved at 09:20. Can it support a simulated 09:10 decision?

Answer: Not without independent evidence that the system could have obtained that information by 09:10. Event time and availability time are different. Record the gap rather than assigning the earlier timestamp to the decision.

4 A split trap

A label at 10:00 uses returns through 10:30. Validation starts at 10:15. Can the 10:00 example safely remain in training merely because its start time is earlier?

Answer: No. Its outcome window overlaps validation. Define purging and any additional gap using the actual information horizon and evaluation design.

5 A fill trap

A bar has high 105 and low 95. Your long has target 104 and stop 96. What happened first?

Answer: The bar does not establish the order. Use an explicit conservative policy, classify the case as ambiguous or obtain finer data. Choosing the target first because it helps the result is invalid.

6 A monitoring trap

The supervisor heartbeat updates every minute, but there are no new qualified chunks or completed trials. Has research progressed?

Answer: Liveness has been observed; research progress has not been established. The dashboard should show both separately and explain the blocker.

7 A quota trap

The manual allowance is 300 requests and the shared daily allowance is 480. Research has already reserved 250. How much room can the manual session use if it has used zero and no other participating job runs?

Answer: At most 230 under the shared budget, not 300 plus 480. External account usage may reduce actual provider headroom further. Local counters are not necessarily an account-wide broker meter.

8 A model trap

A model has 95% accuracy where 95% of labels are negative. Has it demonstrated useful prediction?

Answer: Not necessarily. Predicting negative every time achieves the same accuracy. Compare a baseline, class-specific errors, calibration and the economic decision being made.

9 A citation trap

An AI cites a paper that mentions momentum. Its answer claims the paper proves a net-profitable Indian intraday strategy. Is that supported?

Answer: Only if the cited evidence actually establishes that claim under the relevant market, horizon, costs and validation design. Topic similarity is not entailment. The answer may need to narrow its claim or mark it unsupported.

10 A recovery trap

A worker wrote a completed chunk but crashed before recording completion. Should the restart download everything again and append it?

Answer: First reconcile persisted output using the job ID and integrity checks. Idempotent handling should recognize valid completed content and avoid duplication. An uncertain or partial file needs explicit recovery, not blind trust.
